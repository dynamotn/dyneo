# Working on DyNeo

DyNeo is this Neovim configuration. It is a git submodule of the chezmoi
dotfiles (`~/Dotfiles/home/private_dot_config/nvim`, also reachable as
`~/Dotfiles/silos/neovim`) and the parent repository's rules still apply:
the machine-wide agent rules in `~/.config/AGENTS.md`, and
`~/Dotfiles/CLAUDE.md`. These notes cover what is specific to this tree.

## Before you start

- Check for parallel work first. Other agent sessions often run on this tree
  in `.worktrees/*`; look at `git worktree list` and
  `git log main..<branch> --name-only` for branches touching the same files,
  and order or rebase overlapping work instead of colliding with it.
- Work in a worktree under `.worktrees/` (`git wt <branch>`), on a branch, and
  finish with local commits. Never push.
- "Fix" or "optimize the config" means auditing every area -- `lua/config`,
  `lua/plugins`, `lua/tools`, `lua/util`, `lsp/`, `plugin/`, `ftplugin/`,
  `scripts/` -- by reading the code, not just running the checks. A green
  suite does not show logic bugs or dead and slow code.
- `lazy-lock.json` changes on every `:Lazy update` in the user's editor. Leave
  an uncommitted change to it alone unless the task is about plugins.

## Layout

| Path                      | What it holds                                          |
|---------------------------|--------------------------------------------------------|
| `init.lua`                | globals, `per_machine`, version gate, then `config.lazy` |
| `lua/config/`             | globals, options, keymaps, autocmds, `languages.lua`   |
| `lua/config/languages.lua`| one `DyLangSpec` per language: parser, servers, linters, formatters, dap, tests |
| `lua/plugins/<group>/`    | lazy.nvim specs; `lang/` holds per-language extras     |
| `lua/tools/`              | features built here (runbook, kube, tfplan, sbom, ...) |
| `lua/tools/mason-registry/` | the Mason packages dytoy installs; the rest are in `dynamotn/mason-registry` |
| `lua/util/`               | shared helpers (`sensitive`, `ai_guard`, `forge`, `scratch`, `root`, ...) |
| `lua/dyneo/health.lua`    | `:checkhealth dyneo`                                   |
| `lua/per_machine/`        | `config.lua.tmpl`, rendered by chezmoi; never in a clone |
| `plugin/`                 | thin startup shims: user commands and autocmds that `require` a tool on demand |
| `ftplugin/`, `ftdetect/`, `after/`, `queries/`, `lsp/` | per-filetype settings, detection, queries, server configs |
| `doc/dyneo.txt`           | the help, the canonical place for how things work      |
| `doc/dyneo-keymaps.txt`   | generated by `scripts/keymaps-doc.sh`; never edit by hand |
| `tests/spec/`             | plenary-busted specs mirroring `lua/`                  |
| `scripts/`                | checks and benchmarks run by pre-commit and CI         |

## Naming

- The configuration is **DyNeo**. User-visible names follow it: every
  command is `:Dy*` (so `:Dy<Tab>` lists them all), notification titles
  `DyNeo <area>` from `util.notify.titled`, health `dyneo`, help tags `*dyneo-...*`. There is no `LazyVim`
  global; its old helpers live in `lua/util/*`.
- A command that needs no particular buffer gets a mapping under the
  which-key group of its area (`<leader>k` supply chain and secrets,
  `<leader>i` infrastructure, `<leader>p` project); one that acts on a kind
  of buffer gets a `<localleader>` mapping where that buffer is set up.
- Settings shared across the config are fields of the global table `DyNeo`,
  declared with their default, type and an explanation in
  `lua/config/globals.lua`, and overridden per machine in
  `per_machine/config.lua.tmpl`. Never add a loose `_G.<name>`; `_G.dd` and
  `Snacks` are the only other globals.
- Use lazy.nvim's own `VeryLazy` event, not an alias.
- LuaLS classes are `Dy*` (`DyLangSpec`, `DyProjectSection`). Augroups and
  namespaces of a tool are `dy_<module>`; those of `config` are `dyneo_*`.
- Modules return `local M = {}`. Constants a spec may change are upper-case
  fields (`M.LIMIT`, `M.TIMEOUT`, `M.SUBCOMMANDS`).

## Adding a feature

A feature under `lua/tools/` lands in one commit with everything around it:

1. `lua/tools/<name>.lua` -- the module, loaded only when asked.
2. `plugin/<name>.lua` -- a few lines defining the command (and completion,
   and any `FileType` autocmd) that `require` the module lazily. Nothing
   heavy runs at startup.
3. `tests/spec/tools/<name>_spec.lua` -- and `tests/spec/util/<x>_spec.lua`
   for every new `lua/util/<x>.lua`.
4. `doc/dyneo.txt` -- the section, the command in `|dyneo-commands|`, then
   `:helptags doc`; `doc/tags` is committed.
5. `README.md` -- at most a row or a phrase in the feature table. Rationale
   belongs in the help and in module comments, not the README.
6. Mappings in `lua/config/keymaps.lua` or the plugin spec's `keys`, then
   `scripts/keymaps-doc.sh` to regenerate `doc/dyneo-keymaps.txt`.
7. External binaries it needs reported in `lua/dyneo/health.lua`.

## Languages and tools

A new language or tool is an entry in `lua/config/languages.lua`.

- A tool has up to three names -- `[1]` for conform or nvim-lint, `command`
  for the binary, `mason.package` for the installer -- and the last two are
  written down whenever they differ. A tool Mason lacks gets a package: one
  with a release purl in `dynamotn/mason-registry` (its own repository,
  checked out under `DyNeo.dev_plugins_path`) until upstream takes it, one
  installed by dytoy (`dytoy:<tool>`) in `lua/tools/mason-registry/`, or
  `mason = { enabled = false }` when it comes from the system.
- A server is given every filetype of the language that names it. One that
  suits only a dialect lists its own: `{ 'helm_ls', filetypes =
  { 'yaml.helm-values' } }`, or it attaches to every YAML buffer.
- A conditional server's `enabled` is `fun(bufnr)`, decided per buffer from
  where that buffer lives (`vim.fs.root(bufnr, ...)`), never once at startup
  from the working directory.
- `['*']` (every buffer) and `['_']` (fallback for a filetype with no linters
  of its own) are pseudo-languages, not filetypes; never hand them to a
  server.
- A tool's options sit on its entry. Conform keys options by tool name, so a
  tool serving two dialects gets one shared definition that reads the buffer,
  not two entries where the last one read wins.
- Anything built from `config.languages` walks it in sorted order, and only
  the language that owns a parser speaks for it: `pairs` order is not stable
  across sessions.
- A non-obvious tool choice gets a comment above its entry.
- Custom nvim-lint linters live in `lua/lint/linters/<name>.lua`; per-server
  settings in `lsp/<server>.lua`; one that must override what nvim-lspconfig
  ships (its `cmd`, say) goes in `after/lsp/<server>.lua`, since `vim.lsp`
  merges the runtimepath in order and the plugin's file comes after `lsp/`.
- `after/queries/<lang>/` extends upstream queries; `queries/<lang>/` replaces
  them, and is only for overriding a broken upstream query.
- Harper parses by the LSP `languageId`: a compound or unusual filetype is
  mapped to a grammar it knows. Its dictionary is a merged copy of
  `spell/*.txt` in `stdpath('state')`, since it rewrites the file on every
  added word.
- A new filetype needs a sample in `scripts/lib/samples.lua` (or an entry in
  its file-name map), so `check-startup` opens it.

## Code rules learned the hard way

Every one of these came from a bug that shipped. Keep to them.

- **Never block the main loop.** Run external commands with
  `util.system.run` (deadline, output cap, answer on the main loop), not
  `vim.system():wait()` on the UI path; do git and network work in the
  background, a few at a time with `util.system.each`. Where a caller must
  wait (`BufWriteCmd`, a server request), use `util.system.sync`: a bare
  `:wait()` returns nil when a child outlives the deadline.
- **Every external call has a timeout** and a way to fail quietly: a hung CLI
  must not stall typing, a commit, or a quit. A tool that may prompt runs with
  `detach = true` so it cannot fight the TUI for the terminal.
- **Cap what you read.** Output kept in memory has a size limit and says it was
  cut (runbook 1 MiB, plugin review 4 MiB).
- **Fail loudly and closed.** A fetch that failed must not read as a clean
  result; a security check that cannot run blocks instead of passing. Say why
  a section or a tool was skipped.
- **Ask before anything destructive or untrusted** -- running a file's blocks,
  `kubectl apply`, overwriting a file -- and do exactly what was confirmed, in
  the context that was shown.
- **Secrets never leave.** Check `util.sensitive` / `util.ai_guard` before
  handing text to any AI, LanguageTool, or workspace diagnostics. Logs keep
  paths and ranges, never text. A token goes only to the host it belongs to,
  never to a URL taken from a repository.
- **Leave no clear text behind.** Remove temp files holding decrypted text;
  keep sensitive buffers out of undo, swap, backup, shada and the clipboard;
  guards that matter from the first buffer are installed from `plugin/`, not
  from `VeryLazy`.
- **Never discard user edits**: no `:e!` or reload over a modified buffer.
- **No stacked handlers or retries.** Augroups use `clear = true`; reopening a
  buffer must not add a second autocmd; a failing install is tried once per
  session.
- **Compare paths with a separator**, so `/x/proj` does not contain
  `/x/proj-other`; normalize and resolve symlinks first.
- **Keymaps go through `map`** (`util.plugin.safe_keymap_set`), never raw
  `vim.keymap.set`. `keymaps-doc` fails on a mapping a plugin's `keys`
  silently overrides and on a global key given two meanings. Remember the
  terminal stack: `<C-s>` is the zellij prefix.
- **Stay lazy.** Load on filetype, command or key; cache what statusline and
  redraws ask, invalidated by events. Watch `README.md`'s benchmark.
- **Lazy installs register through `util.lazy_install.on_filetype`**, never
  one `FileType` autocmd per tool, and its handlers are idempotent.
- **Nothing per keystroke shells out.** A completion source that runs a CLI
  answers from words it keeps, read again in the background (as the tmux,
  zellij and kitty sources do); `enabled()` answers are cached per buffer.
- **Write-time work is deferred and skipped while quitting** (`QuitPre`,
  `vim.v.exiting`): `:wq` must not kill a lint mid-run and fail a
  `git commit`.
- **`plugin/` code runs under `nvim --clean` too**, before lazy.nvim has
  loaded anything; ask `lazy.core.config` or wait for `User LazyLoad`.
- **Fast events allow only fast APIs.** `vim.print`/`dd` may be called from
  one; never call `nvim_list_uis()` and the like there.
- **Trust before running project code.** A project `.nvim` folder joins the
  runtimepath only through `vim.secure.read`; pin the verdict before
  prompting, since the prompt keeps handling events and would ask again.
  Secret scanners run with live validation off, so nothing is sent to a
  provider to check it.
- **Colorscheme integrations are listed by hand** (`auto_integrations =
  false` in catppuccin); a new plugin with one is added there.
- **Per-filetype options live in `ftplugin/<ft>.lua`**, not in a global
  `FileType` autocmd. Anchor `ftdetect` patterns to their project, not to a
  bare file name.
- Prefer upstream plugins over forks; return to upstream once a fix lands.
  Never pin a moving branch -- pin a commit.

## Comments and docs

- Comments say *why*, in the present tense, about the code as it is. Never
  mention removed code, a past bug, or the fix that introduced a line; that
  is what commit messages are for.
- Document functions with LuaLS annotations (`---`, `---@param`,
  `---@return`, `---@class`) and keep `.luarc.json` diagnostics clean.
  Backticks name identifiers, commands and files.
- In `doc/dyneo.txt`, rule sections with dashes, not `=`: five `=` in a row
  trip the merge-conflict hook.
- Style is StyLua (`.stylua.toml`: 80 columns, 2 spaces, single quotes,
  parentheses always). Do not hand-format against it.

## Tests

- Specs mirror `lua/`: `lua/tools/kube.lua` -> `tests/spec/tools/kube_spec.lua`.
  A fix comes with a spec that fails without it.
- Use `tests/helpers.lua`: `h.unload(...)` the module under test in
  `before_each`, `h.stub` and restore, `h.tmpdir` with its cleanup,
  `h.buffer`, `h.globals`. Fake an external CLI with a script on a private
  `$PATH` instead of depending on what the machine has.
- Specs must pass on a clean CI runner with no parsers, formatters or
  servers installed.
- When `check-startup` fails only because of the machine it runs on (no
  tree-sitter CLI, Copilot not signed in), stub the plugin with
  `before_config` in `scripts/lib/samples.lua`; do not change the config.
- Never name a file with a chezmoi prefix (`encrypted_`, `private_`,
  `executable_`, `dot_`, ...): this tree is a chezmoi source, and chezmoi
  reads the prefix as an attribute. `literal_encrypted_spec.lua` exists for
  that reason.

## Plugins, channels and supply chain

- Two channels: `DyNeo.plugin_channel = 'latest'` (plugin `main`, Neovim
  nightly, `lazy-lock.json`) and `'stable'` (releases, Neovim 0.12,
  `lazy-lock.stable.json`). Each writes only its own lockfile; CI tests both.
- Plugin bumps are their own `chore: update version of plugins` commit.
  Renovate deliberately leaves lockfiles to lazy.nvim, and covers pre-commit
  hooks and workflow actions; the purls of the Mason packages are bumped in
  `dynamotn/mason-registry`.
- A plugin whose last release lags what the config needs goes in
  `stale_releases` in `lua/config/lazy.lua`, with a comment saying why, so
  `stable` follows its branch.
- A local checkout of a plugin is `dev = true` under `DyNeo.dev_plugins_path`
  with `fallback = true`, so other machines still clone it.
- Releases wait `DyNeo.quarantine_window` (a week) before Mason or lazy.nvim
  installs them. Use that one global; never a copy of the constant.
- `lua/per_machine/config.lua` comes from chezmoi. Changing a per-machine
  default means editing `config.lua.tmpl` and checking it renders; the
  encrypted `encrypted_*.lua.age` files are off limits.

## Checks before reporting work done

```sh
scripts/test.sh [path]                                  # plenary-busted specs
scripts/check-startup.sh                                # load it all, open each language
nvim --clean --headless -l scripts/validate-tools.lua   # tool names vs conform/lint/lspconfig/Mason
scripts/keymaps-doc.sh                                  # regenerate and check mappings
prek run --all-files                                    # all of the above, StyLua, private keys, bench
```

Run at least the specs for what changed plus `check-startup.sh` for any Lua
change, and say which ran. A broken startup is the user's real editor broken:
in `mode: symlink` the tree is what Neovim loads.

Both channels are in daily use, so run these checks on each of them. The
channel follows the Neovim that starts (`latest` on a nightly, `stable` on a
release): the plain commands above test `latest`; for `stable`, run the same
commands under the released Neovim from mise, with its own data directory (as
the user's `nvims` does), so its plugins and lockfile never touch `latest`'s:

```sh
export NVIM_APPNAME=nvim-stable   # in fish: set -lx NVIM_APPNAME nvim-stable
mise exec neovim@stable -- scripts/test.sh [path]
mise exec neovim@stable -- scripts/check-startup.sh
mise exec neovim@stable -- nvim --clean --headless -l scripts/validate-tools.lua
mise exec neovim@stable -- scripts/keymaps-doc.sh && git diff --exit-code doc/
```

`doc/dyneo-keymaps.txt` is committed as `latest` generates it; a diff after
the `stable` run is a mapping that differs between channels, to fix rather
than commit. Report the result of each channel separately.

## Commits

- Conventional Commits, enforced by `.gitlint`: `type(scope): subject`, with
  the scope a module or language (`runbook`, `kube`, `lsp`, `keys`, `go`).
- The subject is the outcome a user sees, lower case, imperative, about 50
  characters: "send a token only to its own host", "say when an ACP agent has
  no models", "cap a run's output at 1 MiB".
- A body, when needed, gives the concrete failure and why, then the fix in a
  sentence; side fixes go under "Also: ...". No headings, no trailers.
- Older history has unscoped subjects ("fix: portability"); do not copy them.
- Branches land on `main` as a plain `Merge branch '<branch>'` commit, done
  by the user; keep a branch's commits clean enough to merge as they are.
- There is no `CHANGELOG.md`; do not create one.

## Gone, do not bring back

- Loose globals (`_G.plugin_channel`, `_G.enabled_languages`, ...) and
  `LazyVim.*` / `lazyvim.util.*` calls: all replaced by `DyNeo.*` and
  `lua/util/*`.
- Reloading a buffer with `:e!` after a parser installs; the buffer is set
  up again instead.
- gitleaks (now betterleaks), editorconfig-checker (removed), nvim-dap-ui
  (now nvim-dap-view).
