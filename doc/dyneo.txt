*dyneo.txt*   DyNeo, a Neovim configuration for DevOps and SA work

                                                                       *dyneo*

The name reads two ways.  Said aloud, DyNeo is a playful spelling of the
Vietnamese "đi nào" -- "let's go", the cute way of saying it.  Written down,
it is Dy, from dynamo, the author's handle (and the prefix of every command
this setup defines, |:DySpell| and the rest), plus Neovim.

This is DyNeo, a standalone lazy.nvim configuration, not a distribution to
install over yours.  Every language it knows about is one declarative entry in
`lua/config/languages.lua` -- its Treesitter parser, LSP servers, linters,
formatters, debug adapters and test runners -- and a single |FileType|
dispatcher installs that entry the first time a file of the language is
opened.

The same tree runs on a laptop with everything enabled and in a container with
four languages; what differs is a handful of globals, see
|dyneo-per-machine|.

------------------------------------------------------------------------------
1. REQUIREMENTS                                           *dyneo-requirements*

Running at all          Neovim 0.13+ (nightly), or 0.12+ on the `stable`
                        channel.  An older Neovim stops at an error message
                        instead of loading anything.
Bootstrapping plugins   git
Icons                   A Nerd Font in the terminal.
Mason downloads         curl, tar, unzip, gzip
Treesitter parsers      A C compiler, and the tree-sitter CLI.
Pickers, completion     ripgrep, fd

Everything else is installed lazily.  Many Mason packages are built by a
language toolchain, so what Mason can install depends on what is on $PATH:
node/npm (or bun), python3/pip (or uv), go, cargo, java, and so on.  `bun` and
`uv` are used in place of `npm` and `pip` when they are installed.

Some tools are never installed by Mason and must come from the system, or from
the language's own toolchain.  They are the entries marked
`mason = { enabled = false }` in `lua/config/languages.lua`; a missing one is
skipped, not reported as an error.

Optional: `pngpaste` (macOS) or `wl-paste`/`xclip` (Linux) to paste images,
`fcitx5-remote` to switch input method, and `d2` with one of `rsvg-convert`,
`resvg` or `magick` on a kitty-graphics terminal for |dyneo-diagram|.

------------------------------------------------------------------------------
2. INSTALL                                                     *dyneo-install*

Back up whatever is there and clone the repository to `~/.config/nvim`: >sh

    mv ~/.config/nvim ~/.config/nvim.bak
    git clone https://gitlab.com/dynamo-config/neovim.git ~/.config/nvim \
        --single-branch --depth 1
<
To try it beside an existing configuration instead of replacing it, clone
anywhere and run it under its own name with |$NVIM_APPNAME|: >sh

    git clone https://gitlab.com/dynamo-config/neovim.git ~/.config/dynamo \
        --single-branch --depth 1
    NVIM_APPNAME=dynamo nvim
<
The first `nvim` clones the plugins; the first file of a language installs
that language's parser, servers and tools.  `:Lazy` shows the first half,
`:Mason` the second, and `:checkhealth dyneo` what the requirements above
are missing.

3. CONFIGURATION                                         *dyneo-configuration*

3.1 Per machine settings                                   *dyneo-per-machine*

chezmoi is not needed.  It renders `lua/per_machine/config.lua.tmpl` into
`lua/per_machine/config.lua` on my machines; in a plain clone that file does
not exist, the loader stays quiet about it, and the defaults in
`lua/config/globals.lua` stand.

To change them, write `lua/per_machine/config.lua` by hand and assign the
globals there.  `init.lua` loads it before anything else, so every global in
|dyneo-globals| is still open to it: >lua

    DyNeo.dark_mode = false
    DyNeo.plugin_channel = 'stable'
    DyNeo.enabled_languages = { 'lua', 'bash', 'markdown' }
    DyNeo.enabled_plugins.obsidian = true
    DyNeo.obsidian.paths.personal = vim.fn.expand('~/Notes')
<
An error raised inside that file is reported; only its absence is silent.

3.2 Globals                                                    *dyneo-globals*

Every global is a field of the one global table `DyNeo`, declared, typed and
defaulted in `lua/config/globals.lua`.

                                                             *DyNeo.dark_mode*
`DyNeo.dark_mode`              (default `true`)
        Background to use, whenever the clock is not in charge.

                                                             *DyNeo.day_night*
`DyNeo.day_night`              (default `{ enabled = false, day_start = 6,`
                          `night_start = 18 }`)
        With `enabled` on, the clock drives `DyNeo.dark_mode` and the
        colorscheme follows it.  With it off, `DyNeo.dark_mode` is the only
        thing consulted.

                                                        *DyNeo.plugin_channel*
`DyNeo.plugin_channel`         (default `'latest'` on a nightly,
                          `'stable'` on a release)
        `'latest'` or `'stable'`, see |dyneo-channels|.

                                                     *DyNeo.quarantine_window*
`DyNeo.quarantine_window`      (default: one week, in seconds)
        How long a release waits before Mason or lazy.nvim may install it;
        `0` turns the wait off.  See |dyneo-quarantine|.

                                                     *DyNeo.enabled_languages*
`DyNeo.enabled_languages`      (default: every supported language)
        Which languages get plugins, parsers and tools at all.

                                                      *DyNeo.bundle_languages*
`DyNeo.bundle_languages`       (default `{}`)
        Languages whose tooling is installed up front rather than on first
        use, for containers and prebuilt images.

                                                       *DyNeo.enabled_plugins*
`DyNeo.enabled_plugins`        (default: all `false`)
        `obsidian`, `leetcode`, `otter`, `firenvim`, `chezmoi`.

                                                     *DyNeo.used_full_plugins*
`DyNeo.used_full_plugins`      (default `false`)
        Install every plugin, to refresh the lockfile.

                                                              *DyNeo.obsidian*
`DyNeo.obsidian.paths`         (default `{ personal = '~/Documents/Notes' }`)
        Vault name to folder.  `DyNeo.obsidian.vaults()` and
        `DyNeo.obsidian.todo_path()` are built from it and may be replaced
        too.

                                                      *DyNeo.yaml_schema_dirs*
`DyNeo.yaml_schema_dirs`       (default `{}`)
        Local schema folders offered by |dyneo-schema|, next to the
        ones found in the project.

                                                     *DyNeo.dictionaries_path*
`DyNeo.dictionaries_path`      (default `$XDG_CONFIG_HOME/dictionaries`)
        Folder of word lists (`*.txt`), fed to the dictionary completion
        source and to |:DySpell|.  Nothing breaks when it is missing.

                                                      *DyNeo.dev_plugins_path*
`DyNeo.dev_plugins_path`       (default `$NVIM_DEV_PLUGINS`, else
                          `~/Working/community/nvim`)
        Where plugin specs marked `dev = true` are looked for.  One missing
        from there is cloned from its git remote, so the folder need not
        exist.

                                                *DyNeo.firenvim_site_settings*
`DyNeo.firenvim_site_settings` (default `{}`)
        Per-site `priority` and `takeover` for the browser embedding.

                                                         *DyNeo.test_strategy*
`DyNeo.test_strategy`       (default `'toggleterm'`, `'zellij'` inside zellij)
        How vim-test runs a test.

                                                    *DyNeo.completion_sources*
`DyNeo.completion_sources`     (default `{}`)
        Completion sources named in the completion menu.

                                                                 *DyNeo.ai*
`DyNeo.ai.target`              (default `'avante'`)
        Where |:DyAi| sends a prompt: `'avante'`, or `'sidekick'` for the
        AI CLI open in sidekick's terminal.
`DyNeo.ai.commit_command`      (default `{ 'claude', '-p' }`)
        Writes a commit message for |dyneo-ai-commit|, given the prompt on
        its standard input.  It runs without a terminal, so it must answer
        on standard output without asking anything.
`DyNeo.ai.commit_timeout`      (default 90 seconds, in milliseconds)
        How long `commit_command` may take.
`DyNeo.ai.local_only`          (default `{}`)
        Folders whose code may only go to an AI on this machine, besides
        any project that says so itself; see |dyneo-ai-local|.
`DyNeo.ai.local_providers`     (default `{ 'ollama' }`)
        Avante providers that run on this machine.
`DyNeo.ai.local_command`       (default unset)
        What writes a commit message or a pull request where AI stays
        local, in place of `commit_command`: `{ 'ollama', 'run',`
        `'qwen2.5-coder' }`, say.  Unset, those are refused there.

3.3 Plugin channels                                           *dyneo-channels*

                `latest`                  `stable`
Plugins         newest commit           newest release, or their branch
                                        when they tag none
Neovim          0.13 nightly            0.12 or newer
Lockfile        `lazy-lock.json`          `lazy-lock.stable.json`

Each channel writes only its own lockfile, so a machine on `stable` and a
machine on `latest` never rewrite each other's pins.  The default follows the
Neovim running: a nightly gets `latest`, a release gets `stable`.

`latest` follows the newest Neovim and the newest plugin commits, so an
upstream break can land with any `:Lazy update`.  Set
`DyNeo.plugin_channel` to `'stable'` on a machine that should not ride along.

3.4 Updating plugins                                            *dyneo-update*

An update is a week behind on purpose: the quarantine only lets `:Lazy update`
move to a commit, or a release, that has been out for seven days.  `:Lazy
restore` and a pinned plugin are not touched by it, see
|dyneo-quarantine|.

The lockfile is the snapshot to roll back to, and both live in the
repository, so:

    1. Commit the lockfile before `:Lazy update`, so the working pins are in
       git.
    2. Update, then commit the new lockfile once everything still works.
    3. If an update breaks something, put the previous lockfile back: >sh

        git restore lazy-lock.json
        # or: git checkout <commit> -- lazy-lock.json
<
       then run `:Lazy restore`.  A single plugin can be restored from its
       line in `:Lazy`.

4. LANGUAGES                                                 *dyneo-languages*

110 entries over 144 filetypes: 56 programming languages and frameworks, 54
tools and markup languages.  The authoritative list is
`lua/config/languages.lua`, and each entry is a `DyLangSpec`: >lua

    ---@field filetypes string[]
    ---@field parser? string|DyParserSpec
    ---@field injected_parsers? string[]
    ---@field ext? string
    ---@field lsp_servers? (string|DyLspSpec)[]
    ---@field linters? (string|DyLinterSpec)[]
    ---@field formatters? (string|DyFormatterSpec)[]
    ---@field null_ls? DyNullLsSpec[]
    ---@field dap? (string|DyDapSpec)[]
    ---@field test? string[]
    ---@field neogen? string
    ---@field dial? fun(augend: Augend): Augend[]
    ---@field autopairs? fun(filetypes, rule, cond, ts_cond): Rule[]
    ---@field endwise? boolean
    ---@field otter? boolean
<
Adding a language is adding one such table.  Nothing else has to be touched:
the parser, the servers and the tools are installed from it, the statusline
reads it, and `scripts/validate-tools.lua` checks every name in it against
conform, nvim-lint, lspconfig and Mason.

The overseer tasks of each language live beside it, in `lua/config/tasks.lua`,
keyed by the same names.  `<leader>oo` offers the ones for the current file:
run a script, compile and run a C, C++, Rust, Kotlin or Erlang file, render or
check with `typst`, `terraform`, `docker`, `helm` and the like, and inside a
project its build and test tasks, run from the project root.  A task appears
only when its language is in |DyNeo.enabled_languages| and its program is on
`$PATH`; make, just, npm, cargo, mix and the rest of overseer's own templates
are left to it.

`test` names the neotest adapters of a language, and `vim-test` among them
lets vim-test run its files; vim-test is kept away from every other filetype.
`<leader>cn` writes a doc comment with neogen, in the convention `neogen`
names.  A language neogen knows needs none.  The conventions neogen lacks --
Dart, Elixir, Haskell, Scala, Swift, Zig, R, Gleam, OCaml, Perl and fish, and
the dybatpho style of every shell filetype -- are built in
`lua/util/neogen.lua`; a convention neogen ships serves only the filetypes it
has none for, such as `typescript.tsx`.

4.1 Tooling that installs itself                          *dyneo-lazy-install*

One |FileType| autocmd, one table of handlers (`lua/util/lazy_install.lua`).
Opening a Go file installs the Go parser, `gopls`, its linters, its formatters
and `delve`; nothing else in the table runs.

An autocmd per tool would instead leave Neovim a few hundred patterns to walk
on every |FileType| event, and make the augroup name the only thing keeping
two handlers apart -- a name two languages can collide on, in which case one
silently clears the other.

|DyNeo.bundle_languages| is the other end of the same dial: the languages
listed there are installed up front, which is what a container image or a
prebuilt development environment wants.

A tool Mason has no package for -- one that comes from the system package
manager, from mise or from a script -- can still be installed the same way. A
package of the repository's own registry with `source.id = 'dytoy:<tool>'`
hands the install to `dytoy --tool <tool>`, and each of its `bin` entries
becomes a link to the command wherever dytoy put it
(`lua/tools/mason-dytoy.lua`).  A tool already on the machine is only linked,
without dytoy.  When the package manager needs `sudo`, the password is asked
for in Neovim, with |inputsecret()|, and handed to sudo through
`SUDO_ASKPASS`.

4.2 Buffer servers and tools                                *dyneo-statusline*

The statusline counts the language servers and the tools that are up rather
than spelling them out; the full list is one key or one click away.

    `<leader>cL`       Language servers of the buffer
    `<leader>cT`       Formatters and linters of the buffer

Each entry says whether the tool is installed, running, or missing, so a
formatter that quietly never fires stops being a mystery.  Linters and
formatters only ever run when they are actually installed.

4.3 Workspace diagnostics                                    *dyneo-workspace*

`<leader>xw` asks a language server about the whole project, not only the
files that happen to be open, by handing it every file with
`textDocument/didOpen`.

Unlike the plugin it replaces, the file list and the contents are read off the
main loop, so a big repository does not freeze the editor, and each document
is closed again before Neovim opens the same file for real, so no server ever
sees two `didOpen` for one URI.

5. SUPPLY CHAIN AND SECRETS                                   *dyneo-security*

What reaches the editor from outside, and what leaves it.  Every mapping of
this section is under `<leader>k`, except the ones of a decrypted buffer.

5.1 Quarantine                                              *dyneo-quarantine*

Anything freshly published is held back for a week before it may be installed
-- the same window `min-release-age` (npm), `minimumReleaseAge` (bun, pnpm)
and `exclude-newer` (uv) give the rest of these dotfiles, so a compromised
release has time to be caught and pulled before it lands on this machine.  A
plugin is as much of a supply chain as a package from npm or PyPI, and a
bigger one: whatever is in it runs in this editor the next time Neovim starts.

Neither Mason nor lazy.nvim has a setting for it, and each needs a different
answer.

Mason resolves no versions of its own: every package carries its version in
the registry snapshot, so there is nothing to do per package.
`lua/tools/mason-quarantine.lua` pins that snapshot to the newest registry
release older than the window, instead of to the newest one.

lazy.nvim decides what to check out in one function, for `:Lazy update`, for
the hourly checker and for the update the UI offers alike.
`lua/tools/lazy-quarantine.lua` wraps it and hands back the newest commit, or
the newest release, that has been out long enough.  What lazy.nvim then does
with that target is untouched, so `:Lazy restore` still puts the lockfile back
commit for commit, and a pinned plugin stays where it is.  A repository
younger than the window is installed as lazy.nvim resolved it, since the
alternative is not installing it at all.

A commit date is whatever the pusher set, so each target lazy.nvim resolves
is also written down with the time this machine first saw it.  Once a plugin
has been watched for a whole window, a target first seen inside it gives way
to the newest one seen before, however old its date claims to be.  When git
cannot answer at all, a plugin stays on the commit it has, with a warning.

A week of waiting only helps if someone looks.  `<leader>kq` (|:DyQuarantine|)
lists what is held back and for how long; `<leader>kr` (`:DyQuarantine
review`) reads every update on its way, held or already through: the commits
each plugin would move across, and the lines they add that start a process,
load code at runtime, reach the network, touch a credential, delete files,
carry an encoded blob, change the build or add a binary.  Prose, CI and tests
are left out, and a flag raised many times in one file is said once.  A flag
is a reason to read the diff, not a verdict.

5.2 SBOM and vulnerabilities                                      *dyneo-sbom*

What is already installed is the other half.  `<leader>ks` (|:DySbom|) lists
the plugins at their lockfile commits and the Mason packages at the versions
of their receipts as a CycloneDX 1.5 document, and `<leader>ko`
(`:DySbom osv`) asks OSV (https://osv.dev) about them in one request --
names, versions and commits, nothing else of the machine.

The project being edited has a supply chain of its own.  `<leader>kl`
(`:DySbom lock`) reads the lockfile of the buffer, or every one git tracks in
the project (at its top only outside git): `go.mod`, `Cargo.lock`,
`package-lock.json` (npm 7 and later), `uv.lock` and `poetry.lock`.  Their
packages go to OSV in batches of a thousand, and each one with a known
vulnerability gets a warning on its line of the lockfile, its advisories
named, and a quickfix entry.  A package of the project itself is left out.

The container images a file names are checked the same way, see
|dyneo-images|: `<leader>ki` scans them, `<leader>kp` pins them.

5.3 Files kept from AI                                        *dyneo-ai-guard*

A language server is handed the whole text of every buffer it attaches to,
before a single suggestion is asked for.  Opening a `.env` or a private key is
enough to upload it.

What counts as sensitive is listed once, in `lua/config/sensitive.lua` --
dotenv and direnv files, private keys, credential stores -- by name pattern,
by path and by content.  `plugin/ai_guard.lua` then guards every integration
at the one place it reads a buffer or a path: Copilot's `root_dir`, a chat
handed a file, a selection following the cursor into a CLI tool, a prompt on
its way out.

A wrapper that no longer finds what it wraps leaves the plugin as it is and
says so, rather than breaking it on an upstream rename.  A whole project can
keep its code on the machine, sensitive or not, see |dyneo-ai-local|.

`<leader>ka` (|:DyAiGuardCheck|) says why the buffer is held back.  A pattern
that matched something that is not a credential is let past with
`<leader>kA` (|:DyAiGuardAllow|), for that buffer, for as long as it is open;
`<leader>kR` puts it back under the check.

Every decision a guard makes is logged as well, so what left the editor can
be looked back on and not only what was kept in: which integration, which
file, when, and whether it went out or was refused.  Only the path and a line
range are kept, never the text.  `<leader>kL` (|:DyAiGuardLog|) lists this
session, and `:DyAiGuardLog!` every session still in
`stdpath('state')/dyneo/ai_audit.jsonl`.  The same handover is logged once a
minute at most, since Claude Code is handed the selection on every cursor
move.

5.4 Encrypted files                                          *dyneo-encrypted*

A SOPS file, an Ansible Vault, or an `encrypted_*.age` / `encrypted_*.asc`
file of a chezmoi source opens decrypted, and `:w` encrypts it again: SOPS
through `sops edit`, which keeps the data key and the recipients of the
file, Ansible Vault through `ansible-vault encrypt` with its vault id, and
chezmoi through `chezmoi encrypt`, to the recipients of its configuration.
The clear text never reaches the file it came from, and a failed encryption
writes nothing.

Decryption runs in the background, so a slow KMS or a key waiting for its
PIN never freezes the editor.  Until the clear text is in, the buffer shows
the ciphertext read-only.  A decryption that fails, times out or prints more
than can be read leaves the ciphertext as it is.

The buffer is held back from every AI integration before the clear text goes
in (|dyneo-ai-guard|), keeps no swap or undo file, and cannot be undone back
to the ciphertext.  Ansible Vault cannot ask for a password inside Neovim:
give it `ANSIBLE_VAULT_PASSWORD_FILE`, or `vault_password_file` in
`ansible.cfg`.

A diff of ciphertext says nothing, so `<localleader>D` in a decrypted
buffer, or |:DyEncryptedDiff|, diffs its clear text with the clear text of
the file at `HEAD`, or at any revision given, in a split held back the same
way.  The old version goes through the same tool from a private copy in a
directory of its own, both removed once read.

In a sops file, `<localleader>K` (|:DyEncryptedKeys|) lists who can open it
-- the age recipients, KMS keys, PGP fingerprints, GCP, Azure and Vault keys
its metadata names, read off the ciphertext on disk.
|:DyEncryptedRotate| puts a change in place: `<localleader>U` (`updatekeys`,
the default) sets the recipients to what `.sops.yaml` says now, after
someone joined or left; `<localleader>N` (`rotate`) gives the file a new
data key.  Both ask first, need the buffer written, run sops in the
background, and open the file again -- unless it was edited meanwhile, which
they say rather than lose the edits.  Ansible Vault is left out: rekeying it
asks for passwords Neovim cannot type.

5.5 Scanner findings                                          *dyneo-findings*

A scanner run in CI leaves a SARIF report: semgrep, CodeQL, gosec, trivy,
checkov and bandit all write one.  `<leader>kf` (|:DySarif|) reads it -- the
file given, the buffer when it is a `.sarif`, or one asked for -- and lists
every result in the quickfix list, errors first, each with its tool and
rule.  A relative path is read against the base the report gives it, or the
git root of the report.  A path that leads out of that root -- through
`..`, an absolute path, a base of the report's own or a symlink -- is kept
in the list but cannot be jumped to, and says it is outside the project.
A result that is not SARIF is skipped, and the count of those is shown.
Nothing runs; a report over 16 MiB is not read.

In a project with semgrep rules of its own -- `.semgrep.yml`,
`.semgrep.yaml` or a `.semgrep/` folder at its root -- semgrep lints every
buffer with those rules, and only those: never `--config auto` or a
registry pack, and with metrics and the version check off, so no code or
metadata leaves the machine.  The rules come with the repository, so they
run only once trusted: Neovim asks, as for `exrc`, once per session and
again when the rules change, and says when it skips them (`:trust` them to
lint).  semgrep reads the file on disk, so it lints on opening and saving,
not a buffer with unwritten edits.  A rule gives up a file after 5 seconds
or 1 GiB of memory.  A rule that does not parse is reported on the first
line.  semgrep is a large Python package, so it is not installed on its
own: `:MasonInstall semgrep`.

5.6 Detection rules                                          *dyneo-detection*

YARA rules (`.yar`, `.yara`) are highlighted by `tree-sitter-yara`
(https://github.com/dynamotn/tree-sitter-yara), a grammar of YARA 4.5 and
YARA-X written for this configuration, and get the `yls` server, which
compiles each rule on save and reports what does not compile.  A Sigma
rule has no file name of its own, so a YAML buffer with a top-level
`logsource:` and `detection:` is given the Sigma schema (|dyneo-schema|).
Snort and Suricata `.rules` files are Neovim's own `hog` filetype.

5.7 Binary files                                                   *dyneo-hex*

`<leader>kh` (|:DyHex|) opens the bytes of the buffer's file, as they are
on disk, as an `xxd` dump in a `dyhex://` buffer of its own; `:w` there
writes the hex columns back as bytes over the file, and `:e!` dumps the
file again.  It needs no `xxd`.  A buffer with unwritten edits, a sensitive
file (|dyneo-ai-guard|) and a file over 4 MiB are refused.

The offsets are ignored, so deleting a line deletes its bytes.  The text
column is not read, but it must hold one character per byte: a line whose
text column is longer or shorter than its hex, or that is not hex pairs, is
refused with its number and nothing is written.  That catches two lines
joined with `J` or a gap lost between the hex and the text, which would
otherwise write the wrong bytes.  To insert or delete bytes, change as many
characters of the text column (any will do), or add a line of bare hex
digits with no offset and no text column.

Only `:w` of the whole dump writes, and only over its own file: `:w other`,
`:saveas` and `:1,3w` are refused.  So is a file changed on disk since it
was dumped (`:e!` dumps it again), and a write that fails leaves the buffer
modified.

5.8 Debug launch files                                     *dyneo-launch-json*

nvim-dap offers the entries of `.vscode/launch.json` in the working directory
next to the configured ones, and picking one runs whatever program it names.
The file comes with the repository, so it is read only once
|vim.secure.read()| trusts it: Neovim asks the first time, and again after
the file changes.  A refusal holds for the rest of the session; |:trust| it
and restart to change your mind.

6. INFRASTRUCTURE                                                *dyneo-infra*

The files an operator edits, and what to do with them without leaving
the editor: the schema a YAML file is checked against, the cluster a
manifest goes to, the images it runs, the plan a Terraform module would
apply, and the picture of what a directory declares.  Mappings of the
buffer are under `<localleader>`; the ones that need no particular buffer
are under `<leader>i`.

6.1 YAML and JSON schemas                                       *dyneo-schema*

YAML schemas are detected from the content of the buffer -- Kubernetes
manifests, CRDs, cloud-init, Sigma rules.  `<leader>cys`, or
|:DyYamlSchema|, opens a picker to set one for the buffer, `<leader>cym` to
write it in as a modeline, and `<leader>cyr` hands the buffer back to
detection.  Candidates
come from the public catalogs, from the project, from
|DyNeo.yaml_schema_dirs|, and from any path typed in.

6.2 Kubernetes                                                    *dyneo-kube*

A YAML buffer a cluster would take -- a manifest with `apiVersion` and
`kind`, a `kustomization.yaml`, or any file of a Helm chart -- gets mappings
under `<localleader>k`, and |:DyKube| does the same from the command line:

    `<localleader>ke`  Explain the field under the cursor (`kubectl explain`)
    `<localleader>kd`  Diff with the cluster (`kubectl diff`)
    `<localleader>kv`  Validate with a server-side dry run
    `<localleader>ka`  Apply, after a confirmation naming the context
    `<localleader>kr`  Render the chart (`helm template`) or kustomization
    `<localleader>kc`  Switch the context
    `<localleader>kn`  Switch the namespace of the context

The context and the namespace can be switched from any buffer too, with
`<leader>ic` and `<leader>in`.

A manifest goes to `kubectl -f`, a kustomization to `kubectl -k`, and a file
of a chart is rendered first and piped in, with the values file being edited
as its values.  kubectl and helm read the files on disk, so a buffer with
changes not yet written holds the command back: for a kustomization or a
chart, any buffer of its directory.  A diff or a render can hold Secret
data, so its buffer is kept from every AI integration.

`<localleader>ke` reads the field under the cursor off the indentation --
`spec.template.spec.containers.image` -- and the `apiVersion` and `kind` of
its document, and shows what `kubectl explain` says of it in a float.  A key
that is no field, one of `labels` or of the `data` of a ConfigMap, gives way
to the field it sits in.  The schema comes from the cluster, so a CRD is
explained as well as a Deployment.

6.3 Helm values                                                   *dyneo-helm*

In a template of a chart, `<localleader>v` (|:DyHelmValue|) goes from the
`.Values` path under the cursor to its line in the chart's `values.yaml`, or
to the deepest key of it the file sets.  In `values.yaml`, `<localleader>u`
(|:DyHelmUsages|) lists in the quickfix list every template line using the
key under the cursor, and `<localleader>U` (|:DyHelmUnused|) marks the keys
no template uses.  A key is used when a template names it, a parent of it
-- `toYaml .Values.resources` uses all of `resources` -- or a child;
`global` and the values of a subchart are left to their owner.

6.4 Container images                                            *dyneo-images*

A Dockerfile names its bases in `FROM`, a manifest or a compose file in
`image:`; build stages, `scratch` and names holding a variable are left out.
`<leader>ki` (|:DyImageScan|) asks `trivy image` (or `grype`) about each
image once, and puts what it knows on each line naming it: how many
vulnerabilities by severity and the worst of their ids, an error with any
critical or high one.  The first scan downloads the vulnerability database.

`<leader>kp` (|:DyImagePin|) pins each tag to the digest it points at now,
through `crane` or `skopeo`: `nginx:1.27` becomes `nginx:1.27@sha256:…`, so
a tag pushed again does not change what runs.  An image pinned already is
left alone, and nothing is pinned if the file was edited while the registry
answered.

6.5 Policy checks                                               *dyneo-policy*

Infrastructure code is linted against policies as well as for style, each
checker installed by Mason the first time a file of its kind opens:

    `checkov`       Terraform, Dockerfiles and Kubernetes manifests, with its
                  own checks only (`--skip-download`)
    `kube-linter`   Kubernetes manifests, reading `.kube-linter.yaml`
    `conftest`      Kubernetes manifests, against the Rego policies of the
                  nearest `policy/` directory above the file; nowhere else
    `actionlint`    GitHub Actions workflows
    `zizmor`        The security of GitHub Actions workflows -- unpinned
                  actions, template injection, credentials left to the
                  checkout -- offline, asking GitHub nothing

A YAML file is only handed to the first three when it is a manifest, as
|dyneo-kube| tells one apart.  kube-linter and conftest name an object or a
policy, not a line: a finding lands on the line naming its object, or on the
first line.  A checkov check is silenced with `# checkov:skip=<ID>: <why>`
inside the block it is about.

6.6 Terraform plan                                              *dyneo-tfplan*

In a Terraform buffer, `<localleader>p` (or |:DyTfPlan|) runs `tofu plan`,
or `terraform plan` without OpenTofu, in the directory of the file, and
shows what it would do on the blocks that ask for it: `+ create`,
`~ update in place`, `-/+ replace` with the attributes forcing it, and
`- destroy`, as diagnostics walked with `]d`, and all of it in the quickfix
list.  A module call carries every change below it.  The plan runs with
`-lock=false`, and its file -- every planned value in plain text -- is
deleted once read.  `<localleader>P` clears it.

A plan runs the providers and `external` data sources the project names, as
you and with your credentials, so the first plan of a directory in a session
asks first.

`<localleader>d` (`:DyTfPlan drift`) runs a `-refresh-only` plan instead and
shows what changed or was deleted outside the code, on the blocks that
declare it.  It runs only when asked: a refresh reads every object of the
state.

`<localleader>i` (`:DyTfPlan impact`) plans, and shows besides what each
block replaced or destroyed takes with it: every block of the module that
refers to it, or names it in `depends_on`, directly or through another, gets
`↳ depends on aws_instance.web (replace)`.  The graph is read off the
configuration the plan carries -- expressions, `count`, `for_each` and
`depends_on` -- the root module only.  A reference made through a `local`
is not in it, and not followed.

`<localleader>c` (`:DyTfPlan cost`) plans, then hands the plan to `infracost
breakdown` and puts the monthly cost of each block at the end of its line,
summed per module call, with the total in a notification.  The plan goes to
`infracost` through a file only its owner can read, deleted once priced.  A
resource priced by usage alone adds nothing.  `infracost` keeps its own API
key: run `infracost auth login` once.

6.7 Terraform state                                            *dyneo-tfstate*

In a Terraform buffer, `<localleader>s` (|:DyTfState|) shows what the state
holds for the block under the cursor, as `state show` prints it; a block
with a `count` or a `for_each` asks for the instance first, and a module
lists the addresses under it.  `<localleader>o` (`:DyTfState orphans`) lists
what the state holds that no block of the module declares any more -- the
objects the next plan destroys, unless a `removed` or a `moved` block says
otherwise.

`<localleader>I` (`:DyTfState import`) brings an object that exists already
under the resource under the cursor: it asks for the ID and writes an
`import` block above the resource, for the next plan to carry out.  It says
so instead when the state holds the resource already, and asks for the key
of `to` when the resource has a `count` or a `for_each`.

Only `state list` and `state show` run, which read the state and never write
it, with `TF_INPUT=0` so a backend cannot stop to ask for input.  The state
holds every attribute in plain text, so what is shown of it is held back from
every AI integration.

6.8 Architecture diagrams                                 *dyneo-architecture*

`<leader>ia` (|:DyArchitecture|) draws what the directory of the buffer
declares, as D2 in a new buffer to preview (|dyneo-diagram|) or to keep:

    Terraform     each `resource`, `data` and `module` block, and an arrow
                  to every block its body refers to -- read off the files,
                  no plan, state or provider needed
    Kubernetes    each object of the manifests of the directory, and the
                  links the cluster makes: a Service to the workloads its
                  selector matches, an Ingress to its Services, a workload
                  to the ConfigMaps, Secrets, claims and service account it
                  uses, an autoscaler to what it scales.  One named but not
                  in the directory is drawn dashed, `(missing)`.
    Compose       each service, and its `depends_on`

YAML is read through `yq`, a file at a time: a template of a chart (`{{ }}`)
or a file yq cannot read is left out, and named, rather than ending it.

7. OPERATIONS                                                      *dyneo-ops*

Running things and reading what they say: runbooks, logs, certificates,
pipelines and APIs.

7.1 Runbooks                                                   *dyneo-runbook*

In a Markdown file, `<localleader>r` runs the fenced block under the cursor
from the directory of the file, and puts what it printed right under it in an
`output` fence, replaced on the next run.  `sh`, `bash`, `shell`, `zsh`,
`fish`, `python` and `js` blocks run as they are; a `console` block runs only
its `$ ` lines.  `<localleader>R` runs every block in turn and stops at the
first that fails, `<localleader>x` clears the outputs, `<localleader>s` stops
what is running.  A block that deletes, destroys or reaches for root asks
first.  See |:DyRunbook|.

A block can leave a value to the moment it runs: `${input:name}` is asked
for once per buffer and filled in, everywhere it appears, before the block
is checked for what it would destroy -- the check sees the command that
runs.  `<localleader>I` (`:DyRunbook inputs`) forgets the values typed.
`<localleader>F` runs every block from the one under the cursor down, where
a runbook is picked up after a step failed and was fixed.

`<localleader>L` (`:DyRunbook record`) starts a record of the session, and
stops it: each block run is appended, with the time, how it ended and how
long it took, the code as written and what it printed, to a Markdown file
under `stdpath('state')/dyneo/runbook/` that only its owner can read -- the
timeline of an incident, written as it happens.  The code keeps its
`${input:…}`: a value typed for one, a password or a token, is never written
to the record.

7.2 Logs                                                          *dyneo-logs*

|:DyLog| opens a log file, the journal (`journalctl`) or the logs of a pod
(`kubectl logs`) as records, one per line: time, level, message and request
id, whatever the source names them.  `<leader>il` reads the file of the
buffer, `<leader>ij` the journal, and `<leader>ip` starts the command line
for a pod.  JSON lines, logfmt and plain text are read line by line, and the
level is coloured.  At most the last 20000 lines of a file are read, out of
its last 8 MiB, and 2000 of the journal or of a pod.  In the buffer:

    `<localleader>l`   Show only a level and louder
    `<localleader>i`   Show only the request under the cursor; again for all
    `<localleader>f`   Show only the JSON records a `jq` expression selects,
                     as in `select(…)`
    `<localleader>c`   Clear the filters
    `<localleader>r`   Read the source again

Logs carry tokens and personal data, so the buffer is kept from every AI
integration (|dyneo-ai-guard|).

7.3 Certificates and tokens                                    *dyneo-inspect*

`<leader>ii` (|:DyInspect|) decodes what is under the cursor into a split
held back from every AI integration: a certificate -- a PEM block, or its
base64 in a Kubernetes Secret -- through `openssl x509` (subject, issuer,
names, key usage, validity, fingerprint), a certificate request or a public
key the same way, and a JWT read in place: its header, its claims, and
`iat`, `nbf` and `exp` as dates.  The signature of a JWT is never shown, and
a private key is named, never decoded.

`<leader>ie` (`:DyInspect expiry`) checks every certificate of the buffer
and puts an error on one that expired, a warning on one ending within 30
days.

7.4 CI pipelines                                                    *dyneo-ci*

In a `.gitlab-ci.yml` or a GitHub Actions workflow, `<localleader>s` (or
|:DyCiStatus|) asks the forge for the last pipeline of the current branch and
puts the status of each job at the end of the line defining it: `✓` passed,
`✗` failed, `●` running, `○` waiting, `⊘` skipped.  The jobs of a matrix are
counted on their one line, the worst of them shown.  `<localleader>x` clears
them.  The forge is the first of the remotes `upstream`, `gh`, `github` and
`origin` on GitHub or GitLab, asked through `gh` or `glab`, which keep the
token.  `<localleader>e` asks an AI why a failed job failed, see
|dyneo-ai-ci|.

In a `.gitlab-ci.yml`, `<localleader>l` (or |:DyCiLint|) has GitLab check the
saved file with `glab ci lint`, and puts what it finds on the jobs it names.
This sends the file to GitLab, so a file held back from AI is not sent.  A
workflow is checked by `actionlint` and `zizmor` as it is edited
(|dyneo-policy|).

A tag such as `actions/checkout@v4` runs whatever it points at the day the
workflow runs.  In a workflow, `<localleader>P` (|:DyActionsPin|) pins every
`uses:` to the full commit its ref points at now, the ref kept as a comment
for Renovate and Dependabot: `actions/checkout@<sha> # v4`, any comment of
your own kept after it.  Each commit is asked of GitHub through `gh`; a
local action, a `docker://` image and a ref that is already a commit are
left alone, and nothing is pinned if the workflow was edited while GitHub
answered.

7.5 OpenAPI requests                                           *dyneo-openapi*

In an OpenAPI document (`openapi*.yaml`, `openapi*.json`), `<localleader>h`
opens the operation under the cursor as a kulala request, and
`<localleader>H` as a Hurl one (|:DyOpenApiRequest|).  The cursor may be
anywhere inside the method, or on the path for its first method.  The first
server becomes `baseUrl`; each path, query and header parameter becomes a
variable holding its example; a JSON body is made from the example of the
request, or from its schema.  `$ref`s inside the document are followed.  A
YAML document is read through `yq`.  The request opens in a new buffer, to
save where it belongs.

`<localleader>d` (|:DyOpenApiDiff|) compares the document as it is in the
buffer, written or not, with itself at `HEAD` or at any revision given,
through `oasdiff breaking`: each change that breaks a client is an error on
its operation, one that may break it a warning, and the rest notes.  The old
version, and the buffer when it is not written, are put beside the document
under hidden names for the run, so a relative `$ref` resolves from both, and
removed after it.  A run that fails is reported as such, never as nothing
breaking.  Install `oasdiff` once with `:MasonInstall oasdiff`.

7.6 Cron schedules                                                *dyneo-cron*

A schedule says when it runs at the end of its own line, and when it runs
next: `0 9 * * 1-5` reads `⏱ at 09:00 on Mon–Fri · next Mon 12 Oct 09:00,
…`.  The schedules read are the lines of a crontab, the `schedule:` of a
Kubernetes CronJob (or an Argo CronWorkflow), and the `cron:` entries of a
GitHub Actions workflow.  Lists, ranges, steps, month and day names, `7` for
Sunday and the `@daily` family are understood; when both the day of the month
and the day of the week are given, either one is enough, as in every cron.

Times are read in the zone the schedule runs in: local time for a crontab,
UTC for a workflow and for a CronJob without a `timeZone`.  A `CRON_TZ=` or
a `timeZone` naming another zone is said, but no next run is worked out for
it.  A schedule that is no schedule is an error; one that never runs, such as
`0 0 30 2 *`, a warning, and so are a macro or a schedule more often than
every five minutes in a workflow, which GitHub does not run.

`<leader>it` (|:DyCron|) says the same of the schedule on the cursor line in
a notification, and `:DyCron {expr}` of any schedule typed.

7.7 Querying JSON and YAML                                       *dyneo-query*

`<leader>iq` (|:DyQuery|) opens a jq expression on a line of its own above
a split showing what it gives for the JSON buffer -- or a yq expression for
YAML -- and runs it again a moment after the expression, or the buffer,
stops changing.  `<CR>` runs it at once, `q` closes both windows.  The window
bar says how many lines came back, or that the tool failed, with what it
said in the split.

One run at a time: a new one stops the last, a run that takes five seconds
is stopped, and a result over 1 MiB is cut and says so.  The result of a
buffer held back from AI is held back too.

7.8 AsyncAPI documents                                        *dyneo-asyncapi*

A file named `*asyncapi*.yaml` or `.json` is checked against the AsyncAPI
schema of SchemaStore as it is typed (|dyneo-schema|).  In any YAML or JSON
buffer whose first lines name an `asyncapi` version, `<localleader>d`
(|:DyAsyncApiDiff|) compares the document as it is in the buffer, written or
not, with itself at `HEAD` or at any revision given, through `asyncapi diff`:
each change that breaks a consumer is an error on the deepest key of its path
the buffer still holds.  As with |dyneo-openapi|, both versions are put
beside the document under hidden names for the run, so a relative `$ref`
resolves, and removed after it.  Copies a session that ended without
removing them left behind are removed by the next run; a file of that name
DyNeo did not write stops the run and is left alone.  A run that fails is
reported as such, never as nothing breaking.  The CLI runs with its
analytics, which report each command and facts about the document to New
Relic, turned off.  Install it once with `:MasonInstall asyncapi-cli` (it
needs Node 24).

7.9 Protobuf and GraphQL contracts                            *dyneo-breaking*

The two contracts between services left after |dyneo-openapi| and
|dyneo-asyncapi|.  In a `.proto` or `.graphql` buffer, `<localleader>d`
(|:DyBreaking|) compares the schema with itself at `HEAD`, or at any revision
given, and lists each change that breaks a client in the quickfix list.

    Protobuf  `buf breaking`, run from the root of the repository on the
              directory of the `buf.yaml` above the file, against the same
              directory at the revision.  buf reads the module's files on
              disk, so while any buffer under the module is not written
              the run is refused, naming it.  buf runs the check plugins
              its `buf.yaml` lists, so the first run in a module asks
              whether it may; a yes holds for the session.  Each change is
              at its line, with the rule it breaks; a deleted file is
              put on the buffer.
    GraphQL   `graphql-inspector diff`, the schema files beside the buffer
              (`.graphql`, `.graphqls`, `.gql`) at the revision against
              the same files now, the buffer as it is, written or not.  A
              schema split over files is compared as one, so a type moved
              between them is no removal; files in other directories are
              not read.  The tool names types and fields, not lines, so
              each change is put on its field, else on its type, in the
              file that defines it, else on the first line of the buffer.
              Install it once with `:MasonInstall graphql-inspector`.

A revision is a name, a hash or a `~`/`^` path; anything else is refused,
since buf reads options from it.  A run that fails is reported as such,
never as nothing breaking.

8. DATA AND MACHINE LEARNING                                      *dyneo-data*

Data in files and in databases: reading it, querying it, running it
through a REPL or a warehouse, and looking inside the models it trains.
The mappings live under `<leader>D`.

8.1 Data files                                              *dyneo-data-files*

`<leader>Dd` (|:DyData|) sums up the data file of the buffer, or the one
named, in a tab of its own: the columns and their types, the first 50 rows,
and how many rows there are.  `<leader>Ds` gives the statistics of every
column in place of the rows: minimum, maximum, distinct values, mean,
quartiles and how many are missing.  DuckDB reads Parquet, CSV, TSV, JSON
and JSON lines, compressed with gzip or zstd or not (`:MasonInstall
duckdb`).  A pattern such as `:DyData data/*.parquet` reads every file it
matches as one table, so a file whose name holds `*`, `?` or `[` is not read.

A CSV, TSV or pipe-separated `.psv` file lines its columns up as a table
with `<localleader>v` (csvview.nvim), split on the delimiter its filetype
names rather than one guessed from its first lines.  A `.jsonl` or `.ndjson`
file, one JSON value per line, is highlighted and left unformatted.

The pipelines that make data are read too: a Snakemake `Snakefile` or `.smk`
file through its own grammar, and a Nextflow `.nf` file or `nextflow.config`
through Groovy's, which Nextflow is written in.

Opening a `.parquet` file shows that summary in place of its bytes.  The
buffer is no copy of the file and cannot be written over it.

`<leader>Dq` runs the SQL of the buffer, or of the selection, through DuckDB
from the working directory, so a query reads a file by its relative path:
>sql
    SELECT city, avg(price) FROM 'data/sales/*.parquet' GROUP BY ALL;
<
The result opens in a split at the bottom, its first and last rows when
there are more than 50.  A script stops at its first error, which is then
the last thing shown.  Of DuckDB's dot commands only those shaping the
output run (`.mode`, `.maxrows`, `.print`, ...): a script holding `.shell`,
`.system`, `.read` or `.output` is refused, so a `.sql` file from someone
else's repository cannot run a shell command.  Plain SQL reaches files too,
so a run may read and write under the working directory only (a summary,
under the directory of its file), reads no environment variable and loads
no extension; the configuration is locked, so `SET` in a script fails.  The
SQL of a buffer runs once agreed to, the first time in that buffer; a query
typed after `:DyData sql` is your own and runs at once.

Everything runs in the background.  A new run stops the one still going,
and so does closing its window or leaving Neovim.  A run stops after a
minute and its output is cut at 1 MiB, saying so; the row count of a large
CSV reads the whole file and may take that long, so it comes last.  DuckDB
loads no extension, so a format that needs one fails rather than reaching
the network.  What a run prints is rows of the data, which may be personal:
its window is kept from AI (|dyneo-ai-guard|).

8.2 SQL and databases                                              *dyneo-sql*

`<leader>Db` opens the database UI (vim-dadbod-ui) in the right panel.  It
lists the connections added with `:DBUIAddConnection`, named in `g:dbs`, or
given by `$DBUI_URL` and the `DB_UI_<name>` variables of the environment; a
URL typed into `:DBUIAddConnection` is kept in plain text under
`stdpath('data')/dadbod_ui`, so one holding a password is better given
through the environment.  Queries saved from the UI live there too.

In a SQL buffer, once the UI has loaded, `<leader>S` runs the query, or the
selection, on the connection of the buffer, `<leader>W` saves it and
`<leader>E` edits its bind parameters.  Nothing runs on save.  The result
opens in the bottom panel, and `q` closes it.  `:DB {url} {query}` runs one
query without the UI.

Completion offers the tables and columns of the connection, and the SQL
keywords, in `sql`, `mysql` and `plsql` buffers.  `sqlfluff` lints and
formats them: with the project's `.sqlfluff` when there is one, otherwise
in the dialect of the filetype -- `mysql`, `oracle` for `plsql`, and `ansi`
for the rest.

Inside a dbt project, a folder holding `dbt_project.yml`, `<leader>oo` offers
`dbt compile`, `dbt run`, `dbt test` and `dbt show` for the model of the
buffer, named after its file, run from the project root when `dbt` is on
`$PATH`.  A model is a file under `models/`: a macro, an analysis or a
package under `dbt_packages/` gets none of them.

sqlfluff reads the project's `.sqlfluff` in a dbt project too: one saying
`templater = dbt` lints a model as dbt compiles it, and without one the
`{{ ref() }}` and `{{ source() }}` of a model still parse.

A database answers through a connection; a data file answers through
DuckDB, with no server at all (|dyneo-data-files|).

8.3 Cells and the REPL                                            *dyneo-repl*

A Python script splits into cells at each `# %%` line, the way Jupytext,
VS Code and Spyder write them; a `.ipynb` notebook converts to one with
`jupytext --to py:percent`.  `]j` and `[j` move to the next and previous
cell, `ij` selects the code of a cell and `aj` the whole of it, marker
included, line by line.

`<localleader>v` picks the virtual environment of the project (venv-selector)
among those of poetry, pipenv, pyenv, hatch, pixi and conda, and a `.venv` in
the project, where uv puts its own.  It sets `$VIRTUAL_ENV` and `$PATH` and
restarts the Python servers, so completion, the debugger, the REPL and the
tasks all use it, and it comes back by itself the next time a file of the
project opens.  A script declaring its own dependencies (PEP 723, a
`# /// script` block) gets them through `uv sync --script` once you agree,
the first time it opens: that installs what the file asks for.

`<localleader>r` opens a REPL beside the script (iron.nvim): IPython when the
environment has it, `python3` otherwise, taken from `$PATH` as it starts,
so an activated virtual environment is the one used.  Then:

    `<localleader>c`   send the cell under the cursor and move to the next
    `<localleader>s`   send the line, or the selection
    `<localleader>f`   send the whole file
    `<localleader>i`   interrupt what runs
    `<localleader>q`   leave the REPL

The REPL loads with the first of these keys, not with the file.

A Quarto (`.qmd`) document runs its chunks the same way (quarto-nvim):
`<localleader>c` sends the `{python}` or `{r}` chunk under the cursor to the
REPL of its language, without its fences, `<localleader>a` the chunks above
it and `<localleader>A` all of them, `<localleader>s` the line or the
selection.  The language server of each chunk's language
answers inside it, through otter, so it runs where otter is enabled
(|DyNeo.enabled_plugins|).  `<localleader>p` previews the document with
`quarto preview`.  An R Markdown (`.Rmd`) document has the language servers
of its chunks too, and runs them with R.nvim's own keys where R is
installed; R.nvim leaves `.qmd` documents to quarto-nvim.

8.4 Model files                                                  *dyneo-model*

Opening a `.safetensors` or `.gguf` file shows its header rather than its
bytes: the format and the size of the file, how many parameters its tensors
add up to and of which types, its metadata, and every tensor with its type
and shape.  A GGUF vocabulary is counted, not listed, and a long string is
cut to one line.

Only the header is read, a megabyte at a time, so a model of many gigabytes
opens at once.  The file usually comes from elsewhere and nothing in it is
trusted: a length running past the end of the file or past 128 MiB of
header stops the reading, and the buffer says why.  The buffer is no copy of
the file and cannot be written over it.

9. PROJECT AND WRITING                                        *dyneo-features*

The project as a whole, its decisions, and the prose and pictures written
in it.

9.1 Project overview                                           *dyneo-project*

`<leader>pp`, or |:DyProject|, opens one page on the state of the project
of the current buffer: the branch, how far ahead and behind its upstream,
and the files changed; the diagnostics of its open buffers, by file; the
tasks overseer ran; the open merge or pull requests and the last pipeline of
the branch, from the forge of |dyneo-ci|; and the Jira issues assigned
(|:DyJira|).  Each section fills in as its answer comes, or says why it
cannot.  `<CR>` opens the file, the page or the issue of the line, `r` asks
everything again, `q` closes it.  `<leader>pR` (|:DyRoot|) lists the roots
found for the buffer.

9.2 Decision records                                               *dyneo-adr*

|:DyAdr| keeps the architecture decisions of a project as adr-tools does: one
Markdown file per decision, numbered `0001-<title>.md` and on, in the
directory a `.adr-dir` file at the root names, else `docs/adr`, `doc/adr`,
`docs/decisions` or `adr` when one exists, else `docs/adr`.  A `.adr-dir`
naming a directory outside the project is refused.  A record has a
title, a date, a status -- proposed, accepted, deprecated, superseded -- and
its context, decision and consequences.  A decision that replaces another
links both ways: the old one says what superseded it, the new one what it
supersedes.

    `<leader>prr`      Pick a record and open it
    `<leader>prn`      Write a new record
    `<leader>prs`      Set the status of the record open
    `<leader>prS`      Write a record replacing the one open

9.3 Spelling                                                     *dyneo-spell*

|:DySpell|, or `<leader>zm`, rebuilds a spell file with |:mkspell| from the
word lists under |DyNeo.dictionaries_path| and `spell/`: Vietnamese,
Chinese, plus the `proper` and `technical` lists kept in the repository.

Comments are spell-checked as well as prose, through `ltcc`
(languagetool-code-comments), as diagnostics and as code actions.  The word
under the cursor, or a Visual selection for anything with an apostrophe or a
dot in it -- `<cword>` stops at both -- is added to a list with `<leader>zt`
(technical) or `<leader>zp` (proper nouns).

9.4 Diagrams                                                   *dyneo-diagram*

D2 diagrams render inline on kitty-graphics terminals, zellij included.
`<leader>cp` previews the diagram under the cursor; Markdown and Typst get
their own preview on the same key.  The diagram of what a directory
declares is drawn by |dyneo-architecture|.

C4 models are written as code.  A LikeC4 model (`.c4`, `.likec4`) gets its
grammar and its language server, which checks the whole workspace -- every
model file under the root -- as it is typed.  The server runs a
`likec4.config.{js,ts,...}` it finds under the root, so in a root holding
one it starts only once you said it may, asked once a session; a JSON
config needs no asking.  A Structurizr workspace (`workspace.dsl`) gets its
grammar.

In a LikeC4 buffer, `<localleader>p` (|:DyC4|) draws a view of the workspace
here: `likec4 gen d2` writes every view as D2 into a cache of its own, never
into the workspace, and the view picked -- or the only one -- goes to the D2
preview above.  likec4 reads the files on disk, so a buffer not yet written
is refused, and it runs a code config as the server does, so in a root
holding one it asks first, again on each run until you say it may.  A model
with errors is not drawn: likec4 still writes what it could, and its errors
are shown instead.  The root of a workspace is the nearest directory with a
config of any name (`.likec4rc`, `likec4.config.json`, `.ts`, ...), else the
repository.  Install it once with `:MasonInstall likec4` (Node 22).
Structurizr exports PlantUML or Mermaid, not D2, with its own tool.

9.6 AI actions                                                    *dyneo-ai*

Avante, Claude Code and the CLIs of sidekick each have their own keys, under
`<leader>av`, `<leader>ac` and `<leader>a`.  |:DyAi| sits above them: a
prompt about the code under the cursor sent to whichever of them
|DyNeo.ai| names, and one picker, `<leader>ai`, over every AI action of the
configuration with the key that does each.

The prompt and the code go through the same guard as everything else: a
buffer |dyneo-ai-guard| holds back is refused with its reason, and what was
sent is logged by path and line range.  A tool an AI calls through MCP Hub
(`<leader>M`) asks first, unless its server lists it in `autoApprove` of
`servers.json`.

    `<leader>ae`       n, x   Explain the selection, or the whole buffer
    `<leader>ar`       n, x   Review it for bugs and risks
    `<leader>au`       n, x   Write unit tests for it
    `<leader>ao`       n, x   Document it
    `<leader>ax`       n, x   Fix its diagnostics
    `<leader>al`       n, x   Pick a prompt
    `<leader>ai`       n, x   Pick any AI action
    `<leader>ag`       n      Review the staged changes, |dyneo-ai-review|
    `<leader>aG`       n      Describe the branch for its pull request,
                            |dyneo-ai-pr|

A line with a diagnostic also offers "Fix with AI" among its code actions
(`<leader>ca`), on the line or on the selection: the `fix` prompt run over
those lines, as `<leader>ax` does.

Avante's sidebar is dressed like the other panels: the editor's background
and separator, no number or colour columns, and a plain title naming its
provider.  The statusline shows that provider and model once Avante has
loaded, in the warning colour while it answers; a click switches provider.

Prompts                                                    *dyneo-ai-prompts*

A prompt is a Markdown file.  The ones shipped are in `prompts/`; a project
adds its own, or replaces a shipped one of the same name, in
`.nvim/prompts/` -- read only once Neovim has asked whether to trust that
`.nvim` folder, through |vim.secure.read()|, and been told yes, since its
text is sent along with the code; |:trust| takes it back.  An
optional front matter line `description:` names it in the picker.  These
words are filled in:

    `{selection}`     the selection, or the whole buffer, fenced, cut at
                    256 KiB
    `{file}`          the file name, relative to the working directory
    `{filetype}`      the filetype
    `{diagnostics}`   the diagnostics of the selection, one a line
    `{input}`         asked for when the prompt runs

Commit messages                                             *dyneo-ai-commit*

In a commit message, `<localleader>g` (|:DyAi| `commit`) writes the message
from the staged diff with |DyNeo.ai.commit_command|, in the style of the
last ten subjects, and in Conventional Commits when the repository has a
`.gitlint` or commitlint configuration.

The commit message buffer itself is always kept from AI, since `git commit
--verbose` puts the diff in it; the diff is read from git instead, and is
refused when a staged file is one |dyneo-ai-guard| holds back, when it has
the shape of a credential, or when `betterleaks` finds a secret in it or
cannot run.  A diff over 512 KiB is cut, and the prompt says so.  The
message goes where nothing has been typed yet, before the first comment as
`core.commentChar` (or `core.commentString`) spells it, or as git wrote it
for `auto`; one already written is replaced only when you say so.  The prompt is `prompts/git/commit.md`, and a
trusted project may replace it; it is given `{files}`, `{history}`,
`{convention}`, `{diff}` and `{fence}`, a code fence longer than any run of
backticks in the diff.

Reviewing the staged changes                                *dyneo-ai-review*

`<leader>ag` (|:DyAi| `staged`) sends the staged diff to the chat of
|DyNeo.ai| `target` for a review before the commit, where the answer can be
talked over.  The diff is read and checked as for |dyneo-ai-commit|: a
staged file |dyneo-ai-guard| holds back, text shaped like a credential, or a
finding of `betterleaks` -- or `betterleaks` not running -- refuses it.  The
prompt is `prompts/git/review.md`.

Pull request descriptions                                      *dyneo-ai-pr*

`<leader>aG` (|:DyAi| `pr`) writes the title and description of a pull
request for the current branch, from its commits and its diff since the
merge base with the branch it goes into: the remote's default branch, else
`main` or `master`, or the one given to `:DyAi pr {base}`.  The diff is
checked as for |dyneo-ai-commit|, and written up by |DyNeo.ai|
`commit_command`.  The answer opens in a Markdown buffer to edit;
`<localleader>y` there copies it.  Nothing is sent to the forge.  The prompt
is `prompts/git/pr.md`.

Failed CI jobs                                                 *dyneo-ai-ci*

In a pipeline file, `<localleader>e` (|:DyAi| `ci`) asks why a job of the
last run on the branch failed, picking one when several did, with the end
of its log and the file itself.  The log is fetched as |dyneo-ci| fetches
the status, through `gh` or `glab`; colours, timestamps and GitLab's section
markers are taken out, and only its last 48 KiB are sent, once the checks
of |dyneo-ai-commit| have passed over them, since a log may print whatever
the job had in its environment.  The prompt is `prompts/ci/failure.md`.

Keeping AI local                                            *dyneo-ai-local*

A project whose code must not leave the machine -- a client's, or one
under an agreement -- says so with a `.nvim/ai.json` holding
`{ "local_only": true }`, or is named in |DyNeo.ai| `local_only`.  Inside
it, everything that would send text away is refused, with the reason:

    Copilot             does not attach
    Claude Code         is handed no selection and no file
    sidekick            sends nothing to its CLIs
    Avante, |:DyAi|       only ask a provider of `local_providers`
    commit messages,    only run `local_command`, and are refused while
    pull requests       it is unset

The file is read without asking for trust, unlike the rest of `.nvim`: it
can only keep AI local, never let anything out, so a repository gains
nothing by writing one.  A file that does not read keeps AI local all the
same; `{ "local_only": false }` lets a folder inside such a project out
again.  Claude Code and the CLIs still read files themselves when started
inside the project: the guard covers what Neovim hands them.

9.7 Service levels                                                 *dyneo-nfr*

`<leader>pAn` (|:DyNfr|) works out what a system promises from the parts a
request goes through, one after the other.  Each term is one part: `99.9`
(or `99.9%`) a component up 99.9% of the time, `2x99.95` two redundant
copies of one of which either is enough, `rps=200` the load and
`latency=150ms` the mean time a request takes, in `us`, `ms` or `s` (`ms`
when no unit is given): >vim

    :DyNfr 99.95 2x99.9 99.99 rps=200 latency=150ms
<
reads out the availability of the whole, the downtime it allows a week, a
month and a year, the requests it may fail a month (its error budget), and
how many are in flight at once by Little's law, which holds for the mean
latency only, not a percentile.  A year is 365.25 days and a month a twelfth
of it.  Downtime under a second reads `< 1s`, and an availability below 100%
keeps the digits that show it.  Without terms it asks for them.

The same load sizes the system, and each of these terms needs `rps=` above
0.  `size=2KB` is what a request carries, in bytes when no unit is given,
read case by case: `B`, `KB`, `MB`, `GB`, `TB` are decimal as bandwidth is
sold, `KiB`, `MiB`, `GiB`, `TiB` binary, and a lower-case `b` is bits, so
`100Mb` is 12.5 MB and `2kb` 250 B.  `retain=30d` (`h`, `d`, `w` or `y`) is
how long each is kept, `capacity=500` the requests a second one instance
serves, and `peak=3` how many times the average the busiest hour brings: >vim

    :DyNfr rps=200 size=2KB retain=30d capacity=250 peak=3
<
reads out the peak rate, the bandwidth on average (in bytes and in bits a
second, as links are sold), over a month and at peak, the storage that keeps
every request that long, and the instances the peak takes -- and one more,
so that losing one is survived.

9.8 Network ranges                                                *dyneo-cidr*

`<leader>pAc` (|:DyCidr|) reads out the IPv4 range under the cursor: its
network address and mask, its first and last host and how many there are, its
broadcast address, and whether the address written is the network's.

`<localleader>n` in a Terraform buffer (`:DyCidr overlaps`) reads every `.tf`
and `.tfvars` file beside the buffer -- the module -- and puts the ranges that
collide in the quickfix list.  Only the keys that define a network are read:
`cidr`, `cidr_block`, `ip_cidr_range`, `address_space`, `address_prefixes`,
the `*_subnets` lists of the AWS VPC module and the like; never the
`cidr_blocks` a security group lets in.  Only a whole network -- `cidr`,
`cidr_block` or `address_space`, or a key ending in one, outside an
`aws_subnet` and the like -- may hold other ranges: a subnet inside it is
fine.  The same range twice, a subnet inside another subnet, and a network
inside another network are listed.  A range worked out with `cidrsubnet()` is
not read, nor is an IPv6 range: a warning says how many were left out.

9.9 Decision matrix                                             *dyneo-matrix*

Options are weighed in a Markdown table: a row per criterion, its weight in
the second column, a score for each option after it, and a last `**Total**`
row.  `<localleader>m` (|:DyMatrix|) in such a table, in a Markdown buffer,
works each total out again -- the sum of weight times score, an empty score
counting as nought -- puts the best one in bold, and lines the columns up.
Emphasis is read through: `**5**` is 5.  A cell that is no number (`high`,
`4/5`) counts as nought too, and is named with its line in a warning.  A table
with a row wider than its header is left as it is, the rows named: writing it
again would drop the extra cells.  Outside a table it writes one to fill in,
under the cursor; in a decision record (|dyneo-adr|), as its `## Options`
section, just before `## Decision`, so the scores stay with the decision they
led to.

9.10 Well-Architected review                                       *dyneo-war*

`<leader>pAW` (`:DyWar new`) writes a review of the workload as a decision
record (|dyneo-adr|), numbered and dated beside the decisions it leads to: a
section per pillar -- operational excellence, security, reliability,
performance efficiency, cost optimization and sustainability -- and in each
the questions the AWS, Azure and Google frameworks ask, as a checklist.
Tick what holds, add questions of your own, and write what is fixed first
under `## Consequences`.

`<leader>pAw` (|:DyWar|) reads the review open, or the latest of the
project, says how many questions of each pillar hold, and puts the ones still
open in the quickfix list.  Only the items under the six pillar headings are
questions, and only `[x]` holds: `[~]` is still open.  A review is a record
whose `# N.` heading reads `Well-Architected review {date}`; one without a
checklist is warned about, never taken to pass.

9.11 Dependency rules                                             *dyneo-deps*

Which module may use which is a rule a project writes down for a tool to
check.  `<leader>pAd` (|:DyDeps|) finds the one the project of the buffer is
set up for and runs it from the root, off the main loop, for up to two
minutes; every rule broken goes in the quickfix list.  The configuration
nearest the buffer wins, so a service set up for one tool inside a
repository set up for another is checked by its own.  Each of these tools
loads the configuration and code of the project, so the first run in a
project asks whether it may; a yes holds for the session, a no is asked
again on the next run.

    dependency-cruiser  `.dependency-cruiser.{js,cjs,mjs,ts,cts,mts,json}`;
                        the copy in `node_modules/.bin` first, over `src/`
                        when there is one.  Its `baseline` report lists the
                        violations alone and names modules, not lines.
    go-arch-lint        `.go-arch-lint.yml`; each import at its line, the
                        files no component holds, and with `deepScan` each
                        component handed one it may not use, where it is
                        handed.  Warnings past its limit are counted.
    import-linter       `.importlinter`, or `[tool.importlinter]` in
                        `pyproject.toml` or `[importlinter]` in `setup.cfg`;
                        the copy in `.venv/bin` first; each import of a
                        broken contract at its line.

A run whose report cannot be read is said to be a failure, never taken for
a clean result; so is one that exits non-zero with nothing read, since
go-arch-lint and import-linter exit non-zero only when a rule breaks.  None
is installed for you: `npm install -D dependency-cruiser`, `go install
github.com/fe3dback/go-arch-lint@v1.19.0`, `pip install import-linter`.

9.12 Threat models                                              *dyneo-threat*

`<leader>pAT` (`:DyThreat new [{scope}]`) writes a STRIDE threat model of
{scope} -- asked for when not given -- as a decision record (|dyneo-adr|):
its context, for the components, the data flows between them and the trust
boundaries they cross, then a section per category -- spoofing, tampering,
repudiation, information disclosure, denial of service, elevation of
privilege -- with the questions to ask of each boundary, as a checklist.
The threats accepted and the mitigations planned go under
`## Consequences`.

`<leader>pAt` (|:DyThreat|) reads the model open, or the latest of the
project, as |:DyWar| reads a review: how many questions of each category
hold, and the ones still open in the quickfix list.  Only a record whose
`# N.` heading reads `Threat model: {scope}` is a model; another record
that mentions one is not.

13. DEVELOPMENT                                            *dyneo-development*

58 spec files under `tests/spec` run with plenary-busted in a headless Neovim
that loads only the module each spec requires: >sh

    scripts/test.sh                      # every spec
    scripts/test.sh tests/spec/util      # one directory
    scripts/test.sh tests/spec/util/sensitive_spec.lua
<
Plenary and lazy.nvim are taken from lazy.nvim's install directory, or cloned
into `.tests/` when the configuration has never been started.

A case that needs a tree-sitter parser this machine lacks is skipped, except
on CI (`$CI` set), where it fails: CI builds the parsers first with >sh

    nvim --clean --headless -l scripts/install-parsers.lua bash fish ...
<
The rest of the checks: >sh

    scripts/check-startup.sh    # load it all, open a file of each language
    nvim --clean --headless -l scripts/validate-tools.lua
    scripts/keymaps-doc.sh      # rewrite the mapping reference
    pre-commit run --all-files  # the lot, plus stylua
<
All of it runs as pre-commit hooks and in CI, on both plugin channels.

Two benchmarks, because they measure different halves of the same editor: >sh

    nvim --clean --headless -l scripts/bench.lua            # starting Neovim
    nvim --clean --headless -l scripts/bench-filetypes.lua  # opening a file
<
Both rewrite their own section of `README.md` when a number moves by more than
a threshold.  `BENCH_FORCE=1` and `BENCH_FT_FORCE=1` rewrite it regardless,
and `BENCH_FT_ONLY=lua,go` times just those filetypes without touching the
file.
Neither installs anything.

After editing this help file, regenerate its tags with: >vim

    :helptags doc
<

14. TROUBLESHOOTING                                    *dyneo-troubleshooting*

Neovim says it is too old ~
    The version gate in `init.lua` wants 0.13 on the `latest` channel and 0.12
    on `stable`.  Either update Neovim, or set
    `DyNeo.plugin_channel = 'stable'` in `lua/per_machine/config.lua`, see
    |dyneo-per-machine|.

A formatter or linter never fires ~
    `<leader>cT` lists every one the filetype expects, with its state.  A tool
    is only run when it is installed, and the ones marked
    `mason = { enabled = false }` have to come from the system.

A language brings nothing at all ~
    Check that it is in |DyNeo.enabled_languages|.  A language left out of
    that list gets no plugins, no parser and no tools.

An update broke something ~
    Restore the lockfile and run `:Lazy restore`, see
    |dyneo-update|.

Startup got slow ~
    `nvim --clean --headless -l scripts/bench.lua` prints the slowest steps.
    Opening a file is a separate question: `scripts/bench-filetypes.lua`, or
    `BENCH_FT_ONLY=<filetype>` for one of them.

Something is missing from the system ~
    `:checkhealth dyneo` for this configuration's view, `:Mason` for the
    tools, and |dyneo-requirements| for what has to be there first.
